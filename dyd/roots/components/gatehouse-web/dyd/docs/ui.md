# Gatehouse UI

## Presentation boundary

Application pages compose the public API in `src/ui/`. UI components include
controls, typography, navigation, content containers, and layout primitives.
Pages have no presentation HTML, class strings, inline styles, `<style>` blocks,
or direct imports from Bits UI, Lucide, or the shadcn implementation directory.

Existing route/page modules and shared input-form controllers retain application
behavior. They compose the same UI API; they do not define a second component
library. Navigation data and authentication/rename operations are in
`src/app/navigation.ts`, separate from the generic navigation components.

`src/lib/vendor/shadcn/` contains components generated by shadcn-svelte CLI 1.7.0
using the Nova style. The UI API re-exports components where possible and uses
thin adapters for routing, bindable DOM references, imperative dialog handles,
and generic layout. Additional Tailwind utilities are confined to these adapters.
There are no handwritten component CSS rules.
Fullscreen dialog and sheet overlays retain the stock tint without backdrop blur,
which otherwise makes every input repaint reprocess the page behind the modal.

The AST-based `src/ui/architecture.test.ts` checks this boundary for every page,
the access gate, the application entry point, and the standalone file picker.
Workspace and system pages use the shadcn inset sidebar shell. The workspace
switcher stays in the sidebar header on both page families; with system access,
it offers a System administration destination after the workspace list. Sidebar
destinations have Lucide icons; view breadcrumbs and controls stay in the compact
page header. The chat shell is bounded to the viewport, with scrolling contained
to its message feed so the header and composer remain stationary. Jump to latest
is an arrow-down icon button anchored at the bottom right of the feed viewport,
just above the input section, outside the scrolling message content. The sidebar
footer presents the signed-in user name and sign-out action in a dropdown.
Login and full-page loading states use the centered muted-surface card layout.
System administration lists every workspace and can create an enabled or disabled
workspace without adding any workspace membership. Its inventory search and keyset
pagination run on the server.

### System administration page anatomy

System pages compose presentation-only components from `src/ui/`:

- `AdminContent` and `PageBody` use the entire available page width for every page purpose; there are no narrow form/detail width presets.
- `AdminHeader` consistently places titles, descriptions, status badges, identifiers, and actions.
- Directories use a full-width `SearchToolbar`, aligned `RecordTable` columns, and `PaginationFooter`. Each request selects at most 50 records; Previous/Next retain cursor history and replace the current page. Tables retain their column layout and scroll horizontally on narrow screens.
- Detail pages use titled `DetailSection` panels and aligned `Property` rows. JSON/Lisp and rate limits have dedicated displays.
- Create/edit pages share resource-specific field compositions. `FormSection` places the section heading/description beside a fluid field grid on desktop and above the fields on narrow screens. Long editors span the field grid, control heights are consistent, and `FormActions` provides a full-width save/cancel footer. Global providers/models and principal availability have dedicated edit URLs.
- Hubs use the same `NavigationCard` and `NavigationGrid` for system sections and workspace children. Workspace pages fetch only their own metadata for named breadcrumbs.
- `RecordPicker` is a button styled as a reference field that opens a modal search/selector. Its name includes the field label and current selection, the search icon is part of the trigger, and clearing is a separate sibling button. Resource-specific pickers own their API requests; search pages are fetched only when the dialog opens or the user searches/paginates. Selection is a draft until confirmed, cancelling preserves the existing reference, and closing aborts pending search requests. Keyboard navigation, focus trapping, and focus restoration are provided by the owned dialog/picker components.
- Keychain references use the same modal field; their options are the configuration references already supplied by the provider form's existing keychain API.

Each resource retains its own API and data model. Global directory APIs support a
paginated response when `limit` is supplied; existing unpaginated callers retain
their response shape. No generic catalog or cross-resource search is used.

### Workspace page anatomy

Workspace pages use the same presentation components and page-purpose grammar:

- Workspace and project overviews are navigation-only hubs with permanent child navigation cards. They do not load child collections or display recent-item previews. Creation and uploading are available on the corresponding collection pages; project editing has its own page.
- Chat, project, group, file, note, task, secret, type, field, and record directories use aligned tables and bounded server search. Previous/Next replace the displayed page rather than accumulating results. Group directories describe the principal's enabled memberships.
- Project creation/editing, note/task/secret editing, historical note revisions, and record-type field management have dedicated URLs. Session resource URLs open dialogs over the conversation; project resources retain their full-page layouts. Create/edit pairs retain the same fields and section ordering.
- Workspace tools identify resources by names, descriptions, and their meaningful content. Internal IDs are not printed in headers, tables, details, authorship labels, selected-file summaries, or selector dialogs; copyable identifiers are reserved for administration. Resource details use a common header, titled property sections, and separate Markdown content. Secret details remain metadata-only; blank replacement preserves the stored value.
- Project, record-type, record, and file references use modal selectors backed by their own resource APIs. Selected references are hydrated by ID; candidate collections are loaded only when the selector opens or searches.
- Native array collection endpoints retain their body shape. Supplying `limit` opts into bounded search; `X-Next-Cursor` supplies continuation when available. Records retain their existing `records`/`values` bodies and `next_cursor` fields. No generic resource entity or catalog API is introduced.
- Record directories use configured display fields as columns; editors retain drafts across value pages. Field settings are separate from type settings, and the type overview links to Records and Fields.
- Chat keeps its viewport-contained feed above a stationary, full-width card-surface bottom input section, separated by a single top divider. The larger writing area, attachments, and action toolbar share that section with no enclosing input border, rounded input box, shadow, floating overlay, or textarea focus ring. The writing area starts at 6rem tall and grows to a bounded height. Attachments and the icon-only delivery selector sit at the left; a standard icon send button at the right shows upload/submission progress. Selected-file cards show truncated filenames, readable sizes, upload/error states, and separate remove actions in a height-bounded scrolling area. The composer has no instructional footer text. User and agent message bubbles share a 28rem minimum and 42rem maximum width, both clamped to the available width on narrow screens. Input-request forms use the available width, compact sections, and a consistent submit/cancel footer.
- The chat header has standard-sized desktop icon controls for Files, Notes, Tasks, Secrets, and Participants, with accessible labels and tooltips. Rename lives in the overflow menu. Below 768px, one Chat tools dropdown contains labelled resource entries, Participants, and Rename. At narrow widths, ancestor breadcrumbs hide and the chat name truncates as needed.
- Files, notes, tasks, and secrets use content-sized, viewport-bounded dialogs with the Participants collection width; note content and editing can use a wider layout. Headers and action footers remain stationary around one scrolling body. Collections and note history reuse the headerless `RecordList`: integrated search, the same row typography/spacing/dividers, secondary metadata, relevant badges, and file download icon actions. There are no collection table headings, horizontal table scrolling, result counts, or pagination controls on a single page. Creation actions live beside Close in the footer; details have consistent footer actions, and compact editors use Cancel/Save without nested form cards or explanatory section headings. Write-only secret guidance remains explicit. Footer submit buttons retain their native form association.
- Lists, details, creation/editing, note history/revisions, and styled removal confirmations stay within the resource dialog. Removal confirmations retain their opening item name and show failed mutations without dismissing the confirmation. Existing URLs support direct opening and browser Back/Forward; the dialog's Back action goes to the parent view, and closing returns to the conversation. Resource content reuses its request ownership, pagination, mutation, and refresh behavior through `ResourcePage` without nesting another page shell. Opening and closing mount/unmount the selected resource's requests and subscriptions.
- Participants remains a dialog on the chat toolbar. The People/Groups tabs and their Add person/Add group dialogs use the same headerless `RecordList`: integrated search, identical name styling, row spacing, dividers, and scrolling. Existing participants have role labels and icon actions; add dialogs have selection markers. There is no explanatory boilerplate or result count, and pagination controls appear only when needed. Add actions live in the footer. Edit opens a role dialog; Remove opens a confirmation dialog. Failed mutations retain their dialog drafts and expected revisions across background refreshes; cancelling aborts pending work. Grant changes refresh open rosters and chat-directory visibility, and confirmed revocation leaves the affected chat without resetting drafts during ordinary refreshes.
- Capability-based file tools use the full page width, selected-file summaries, filter toolbars, selectable tables, pagination, and a Save selection footer. Capability transport and shared-draft completion remain unchanged.

## Request and draft lifecycle

Each page owns its native resource snapshots, form drafts, and mutation state.
`src/utils/load-state.svelte.ts` supplies request ownership and cancellation;
it does not introduce a generic resource model or transport.

- Before the first successful response, show loading, then an explicit failure
  and retry if the request fails. An empty successful collection is a snapshot.
- Reloading an existing context keeps its content and form controls mounted.
  Pending work and reload failures are separate indicators; transient failures
  retain the last successful data and the user's draft.
- Authentication and access refreshes retain settled claims/access on transient
  failure. Confirmed loss of authentication or access stops the affected work.
  Principal, workspace, owner, resource, mode, and revision changes establish a
  new context; equivalent route resolution and renamed workspace metadata do not.
- Controller activation effects track their intended identity/access inputs and
  execute controller internals through `untrack`. Synchronous cleanup cancels
  requests and subscriptions. Request ownership is checked after decoding and
  before publication, errors, authentication callbacks, navigation, or focus.
- Collection results, applied filters, continuation, and cursor history commit
  after successful requests. Failed search/Next/Previous retain the current page.
- Edit baselines are separate from refreshed snapshots. A conflicting admin write
  preserves the draft and its expected revision; replacing it with the latest
  settings requires the explicit form action.
- Shared input forms keep optimistic answers after a failed patch. Explicit retry
  reads the authoritative draft and reapplies only unsaved field operations;
  invalid answers remain editable, and terminal submission waits for uploads and
  successful writes. Field removal is validated against the descriptor as well.
- Activity reconciliation reports failure to the poller so it can retry rather
  than acknowledging an unsuccessful refresh. Chat refreshes preserve composer
  state and keep agent branches, input cards, and scrolling behavior independent
  of metadata reloads.
- `SessionWorkspace` keeps one conversation mounted per session while resource
  routes change inside its dialog. The conversation retains its draft, selected
  attachments, scroll position, delivery mode, and activity subscription. A new
  session or principal establishes a new conversation. Closing a resource returns
  to the saved conversation route, including direct-agent selection; in-dialog
  navigation moves focus to the dialog header and restores each view's scroll
  position when returning. Collection snapshots, search drafts, applied filters,
  continuation cursors, and cursor history survive list/detail/edit navigation;
  abandoned page requests are cancelled without resetting the settled page.
  Search and pagination changes start the list at the top. A different owner or
  principal resets the resource collection.

Lifecycle regressions compile the real rune modules and route activation scripts
against Svelte's client runtime with controlled promises. These checks require no
browser or DOM and cover failed reloads, access updates, conflicts, overlapping
responses, late decoding, and disposal.

## Theming

`src/app.css` uses the supplied shadcn-generated default light/dark palette and
standard Tailwind mappings. No application-specific CSS variables are defined.
Typography for rendered Markdown uses Tailwind's typography plugin.

`Theme` applies the active workspace theme to the document root, including
portaled dialogs and menus. The default follows the system color scheme.
`setWorkspaceTheme(workspaceID, theme)` accepts light/dark values for documented
shadcn tokens and an optional mode. Switching workspaces clears previous overrides;
system/access pages use the default. No workspace overrides are seeded. A future
branding configuration loader can supply workspace theme data through this API.

## Dryad workflow

Dependencies and generated schemas are supplied through Dryad variants. Never
install dependencies inside the source assets. `.dyd-ignore` excludes
`node_modules`, `dist`, and the Vitest cache from source preservation.

Update dependency manifests/lockfiles in a disposable source environment:

```sh
dryad root develop start dyd/roots/components/gatehouse-web --variant=output=source --scope=none --on-exit=save -- sh -c '"$DYD_STEM/dyd/commands/z-update-lockfile"'
```

Build and check:

```sh
dryad root build dyd/roots/components/gatehouse-web --variant=output=build --scope=none --join-stdout --join-stderr
dryad root build dyd/roots/components/gatehouse-web --variant=output=build-session-file-picker --scope=none --join-stdout --join-stderr
dryad root build dyd/roots/components/gatehouse-web --variant=output=tests --scope=none --join-stdout --join-stderr
dryad sprout run dyd/sprouts/components/gatehouse-web --variant=output=tests --scope=none --join-stdout --join-stderr -- --check
dryad sprout run dyd/sprouts/components/gatehouse-web --variant=output=tests --scope=none --join-stdout --join-stderr
```
